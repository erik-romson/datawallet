# Data Wallet — cross-stack fixtures (companion to `plan.md`)

The fixture suite is the single source of truth for "what bytes do the two stacks agree on?" If Java and Dart disagree, exactly one of them is wrong, and the fixture says which.

This document specifies what's in `spec/fixtures/`, how the bytes are generated deterministically, what each contract test asserts, and how CI runs both stacks against the same files on every PR.

## 1. Repository layout

```
spec/
├── fixtures/
│   ├── README.md                       ; how to regenerate
│   ├── manifest.json                   ; index + sha256 of every artifact
│   ├── inputs/
│   │   ├── handles.json                ; {handle, normalized, valid?}
│   │   ├── passwords.json              ; {pw, kdf_params, kdf_salt_hex, expected_kek_hex}
│   │   ├── keypairs.json               ; deterministic ed25519/x25519 from named seeds
│   │   ├── timestamps.json             ; fixed ts_ms values used in envelopes
│   │   ├── uuids.json                  ; {seed_hex, ts_ms, expected_uuid_hex}
│   │   └── plaintexts.json             ; small string corpus
│   ├── wrapped/
│   │   ├── enc_priv_alice.cbor         ; binary, canonical CBOR
│   │   ├── auth_priv_alice.cbor
│   │   └── …                           ; per-handle, per-password set
│   ├── envelopes/
│   │   ├── basic-1-recipient.cbor      ; final envelope
│   │   ├── basic-1-recipient.signed    ; signed_bytes (envelope minus "signature")
│   │   ├── basic-1-recipient.json      ; same content in JSON for human review (NOT for parsing)
│   │   ├── three-recipients.cbor
│   │   ├── three-recipients.signed
│   │   ├── allow-list-update-v2.cbor
│   │   ├── unicode-description.cbor
│   │   └── invalid/                    ; intentionally bad — used by negative tests
│   │       ├── tampered-ciphertext.cbor
│   │       ├── wrong-issuer-key.cbor
│   │       ├── non-canonical-cbor.cbor
│   │       ├── future-version.cbor     ; version=2
│   │       └── stale-key-id.cbor       ; created_at outside valid_from..valid_until
│   ├── directory/
│   │   ├── pinned-root.cbor            ; the PinnedRoot blob clients embed
│   │   ├── verifier-alice-active.cbor
│   │   ├── verifier-alice-revoked.cbor
│   │   ├── issuer-acme-active.cbor
│   │   └── invalid/
│   │       ├── one-of-two-sigs.cbor    ; below threshold
│   │       └── tampered-public-key.cbor
│   ├── auth/
│   │   ├── nonce-and-signature.json    ; {nonce_hex, expected_signed_bytes_hex, expected_sig_hex}
│   │   └── prefix.txt                  ; the literal 19 bytes "datawallet-auth-v1\x00"
│   ├── audit/
│   │   ├── chain-genesis.json          ; expected genesis prev_hash
│   │   └── chain-3-events.json         ; {events: [...], expected_hashes_hex: [...]}
│   └── fingerprints/
│       └── pubkey-to-fp.json           ; {public_key_hex, expected_fp_render}
└── tools/
    ├── gen.py                          ; regenerates everything from inputs/ (Python + pynacl)
    └── verify.sh                       ; compares regenerated output to committed fixtures
```

`manifest.json` is the single integrity index. Tests assert `sha256` of every file against the manifest first, then load the file. Any drift between committed bytes and the manifest fails CI before any stack-specific test runs.

## 2. Determinism: seeded inputs

All randomness is replaced by named seeds so regeneration is reproducible and a stack's failure can be diffed against the fixture's exact inputs.

### 2.1 Keypairs

`inputs/keypairs.json` lists named seeds:

```json
{
  "alice_enc":   {"type":"x25519",  "seed_hex":"0101...01"},   // 32 bytes
  "alice_auth":  {"type":"ed25519", "seed_hex":"0202...02"},
  "bob_enc":     {"type":"x25519",  "seed_hex":"0303...03"},
  "acme_sign":   {"type":"ed25519", "seed_hex":"04...04"},
  "root_a":      {"type":"ed25519", "seed_hex":"a1...a1"},
  "root_b":      {"type":"ed25519", "seed_hex":"a2...a2"},
  "root_c":      {"type":"ed25519", "seed_hex":"a3...a3"}
}
```

Both stacks derive identical public keys from these seeds:
- Ed25519: `crypto_sign_seed_keypair(seed)` → `(public, private)`.
- X25519: `crypto_box_seed_keypair(seed)` → `(public, private)`. (Stacks lacking a seeded variant convert the seed via `crypto_kdf_derive_from_key` per the fixture's documented derivation step; current libsodium exposes `crypto_box_seed_keypair` in both.)

Each entry's expected derived public key is recorded in `keypairs.expected.json` (separate file, regenerated by `gen.py`). Contract tests load this file and assert the derived public key matches before using the keypair anywhere downstream.

### 2.2 Salts, nonces, random bytes

Wherever the runtime would call `randombytes_buf`, the fixture supplies a fixed value:
- `kdf_salt_hex` per password test.
- `wrap_nonce_hex` per wrapped-blob fixture.
- `ciphertext_nonce_hex` per envelope.
- `data_key_hex` per envelope (so wrappings are predictable).
- `seal_ephemeral_seed_hex` per recipient wrapping (since `crypto_box_seal` uses an internal ephemeral keypair, fixtures use a `crypto_box_seal_with_seed` helper that both stacks expose for testing — if either stack lacks it, fixture wrappings are computed by the generator and stacks verify by **opening**, not by reproducing).

### 2.3 Timestamps

`timestamps.json` lists named instants in ms since epoch (UTC):
```json
{
  "t_register": 1735689600000,
  "t_envelope_basic": 1735776000000,
  "t_envelope_v2":    1735862400000,
  "t_directory_issued": 1735689000000
}
```

### 2.4 UUIDs

`uuids.json` provides the inputs to the deterministic UUIDv7 path (`crypto-formats.md §10`):
```json
[
  {"name":"entry_basic", "ts_ms":1735776000000, "rand_hex":"4242...", "expected":"<uuid>"},
  {"name":"entry_v2",    "ts_ms":1735862400000, "rand_hex":"4343...", "expected":"<uuid>"}
]
```

## 3. What each fixture asserts

### 3.1 Argon2id KEK derivation
- `kek_test`: for each `passwords.json` row, `argon2id(pw, salt, params) == expected_kek_hex`.
- This is the only place where parameter floors are NOT enforced — the fixture deliberately includes both above- and below-floor params so the stack tests cover the rejection path.

### 3.2 Wrapped private-key blob round-trip
- `wrap_test`: given `KEK`, `nonce`, and `private_key`, produce canonical CBOR matching `wrapped/enc_priv_alice.cbor` byte-for-byte.
- `unwrap_test`: given the committed CBOR + KEK, recover the original private key.
- `unwrap_wrong_password_test`: KEK derived from a wrong password produces secretbox failure (no parse error path).

### 3.3 Auth challenge signing
- For each `nonce-and-signature.json` row:
  - `signed_bytes` MUST equal `prefix || nonce` byte-for-byte.
  - Ed25519 signature with `alice_auth` MUST equal `expected_sig_hex`.
  - Verification with the correct public key passes; with a flipped bit, fails.

Ed25519 is deterministic, so signature equality is meaningful. (Both stacks use libsodium, which uses the deterministic variant.)

### 3.4 Envelope canonical bytes — the load-bearing test
For every envelope in `envelopes/*.cbor`:
- Parse the committed canonical CBOR, extract `signature`, re-encode the rest canonically, assert it equals the committed `*.signed` file byte-for-byte.
- Verify `signature` against `acme_sign` public key.
- Generation test (build-from-inputs path):
  - Take inputs (data_key, plaintext, recipients, timestamps, signing key) from `inputs/`.
  - Build the envelope from scratch using the stack's encoder.
  - Assert produced bytes == committed `*.cbor` byte-for-byte.

If either stack's CBOR encoder is non-canonical, the generation assertion fails and the diff localizes which field's encoding is off. The parse/re-encode assertion catches encoders that round-trip non-canonically.

### 3.5 Envelope decryption end-to-end
- Take `basic-1-recipient.cbor` and `alice_enc` private key.
- Verify signature → unwrap data key → check `ciphertext_hash` → secretbox open.
- Plaintext MUST equal `inputs/plaintexts.json["basic"]`.

### 3.6 Negative cases (`envelopes/invalid/*`)
| Fixture | Stack must reject with |
|---------|------------------------|
| `tampered-ciphertext.cbor` | `ciphertext_hash` mismatch (before secretbox) |
| `wrong-issuer-key.cbor`    | signature invalid against directory key |
| `non-canonical-cbor.cbor`  | parse error in canonical mode (or post-parse re-encode mismatch) |
| `future-version.cbor`      | `version != 1` rejected |
| `stale-key-id.cbor`        | `created_at` outside `valid_from..valid_until` of the directory record |

Each negative is a separate test that asserts the rejection path is taken **before** any plaintext-touching code runs. The test inspects which step rejected, so a stack that rejects late (e.g. tries to unwrap before checking signature) fails even if it ultimately rejects.

### 3.7 Directory records
- Verify each `directory/*.cbor` is signed by ≥ threshold (= 2) of the pinned roots from `pinned-root.cbor`.
- `invalid/one-of-two-sigs.cbor` MUST fail threshold check.
- `invalid/tampered-public-key.cbor` MUST fail signature verification on the record itself.

### 3.8 Audit hash chain
- `chain-genesis.json` → genesis `prev_hash` constant (recomputed by stacks from the documented seed string, asserted to match).
- `chain-3-events.json`: feed three events sequentially, assert `hash_n` matches expected for each.

### 3.9 UUIDv7
- For each row in `uuids.json`, generate UUIDv7 with the supplied `ts_ms` and `rand_hex`, assert equal to `expected`.

### 3.10 Fingerprints
- For each row in `pubkey-to-fp.json`, compute the fingerprint per `crypto-formats.md §8`, assert equality.

## 4. Generation — `tools/gen.py`

`gen.py` is the **generator of record**. When fixtures need to change:
1. Edit `inputs/*.json`.
2. Run `tools/gen.py` (Python 3.11+, `pynacl`, `cbor2`).
3. Inspect the diff; commit.
4. CI re-runs `gen.py` and asserts the working tree is clean (`git diff --exit-code spec/fixtures`). A drifted fixture without a regenerated diff fails CI.

`gen.py` uses **only pynacl** (libsodium bindings) — no Java, no Dart. It is a third reference implementation. If the Java or Dart stack disagrees with Python, the most likely culprit is the stack, not Python.

`gen.py` also writes `manifest.json` with `sha256` of every emitted file.

## 5. Stack-specific contract tests

### 5.1 Java (`server/src/test/java/.../FixtureContractTest.java`)
- JUnit 5 test class.
- Fixture path resolved from a system property (`-Ddatawallet.fixtures.dir=…`) or a default of `${project.basedir}/../spec/fixtures`.
- Tests organized as one `@Nested` class per category (KekDerivation, WrappedBlob, Envelope, Directory, Audit, Uuid, Fingerprint).
- Each test reads only the manifest-listed bytes; manifest validation runs in a `@BeforeAll`.
- Tests use `lazysodium-java` for crypto and `jackson-dataformat-cbor` configured for canonical encoding (custom `CBORFactory` with sorted-keys `ObjectMapper`).

### 5.2 Dart (`client/test/fixture_contract_test.dart`)
- `package:test` with one `group` per category, mirroring the Java structure.
- Fixture path from `FIXTURES_DIR` env var, default `../spec/fixtures` relative to the package.
- Uses `sodium_libs` for crypto and `package:cbor` in canonical mode.
- Web build runs the same tests under `dart test --platform chrome` to catch WASM-specific divergence (especially Argon2id at the web floor).

### 5.3 Kotlin (`egnedata-kmp` — external repo)

Kotlin is the **third stack-of-record** for the issuer-side constructions. The egnedata-kmp app
builds and signs envelopes, generates UUIDv7 entry IDs, computes `key_id`, derives fingerprints,
and performs per-recipient key wrapping. Its parity suite must pass against the committed fixtures;
until it does, Workstream D is not complete.

**Fixtures the Kotlin suite must cover:**

| Fixture | Assertion |
|---------|-----------|
| `envelopes/mobile-built/single-recipient.cbor` | Build from inputs → bytes match; signature verifies; alice_enc can decrypt |
| `envelopes/mobile-built/binary-payload.cbor` | Build from binary inputs → bytes match; signature verifies; alice_enc can decrypt |
| `envelopes/mobile-built/binary-payload-multi.cbor` | Build from binary inputs → bytes match; signature verifies; both alice_enc and bob_enc can decrypt |
| `inputs/uuids.json` | UUIDv7 generation from `ts_ms` + `rand_hex` → `expected` |
| `inputs/keypairs.json` | Ed25519 and X25519 `key_id = sha256(public_key)[0:16]` |
| `fingerprints/pubkey-to-fp.json` | Fingerprint derivation per `crypto-formats.md §8` |
| `envelopes/invalid/tampered-ciphertext.cbor` | Rejected before secretbox |
| `envelopes/invalid/wrong-issuer-key.cbor` | Signature invalid |

**Cross-repo acceptance gate:**
The Kotlin parity suite lives in `egnedata-kmp` (owned by the app team) and is **not run by
this pipeline**. The gate is: all eight fixture groups above pass in `egnedata-kmp` CI against
the HEAD of `spec/fixtures/` from this repo. Workstream D is declared done only after that CI run
is green and linked in the delivery checklist.

### 5.4 Python sanity (`spec/fixtures/.../test_self.py`)
- A small `pytest` suite that re-runs the generator's own assertions against committed fixtures. Acts as the canary: if Python disagrees with the committed bytes, the fixtures are corrupt regardless of what the stacks say.

## 6. CI integration

GitHub Actions, three jobs running in parallel:

```yaml
jobs:
  fixtures-self-check:
    steps:
      - run: pip install pynacl cbor2
      - run: python spec/tools/gen.py --check       # asserts no drift
      - run: pytest spec/fixtures
  java-contract:
    steps:
      - run: mvn -pl server -am test -Dtest=FixtureContractTest
  dart-contract:
    steps:
      - run: dart test --platform vm,chrome --tags fixture
```

A PR that touches `spec/fixtures/**` is **required** to also touch at least one of the stack contract tests, enforced by a `CODEOWNERS` rule plus a label-gate workflow. This prevents fixture-only changes from silently weakening contracts (a fixture is only as strong as the tests that consume it).

## 7. Versioning

`spec/fixtures/manifest.json` carries a `spec_version` field matching `ENVELOPE_VERSION`. A v2 envelope ships fixtures alongside under `spec/fixtures/v2/`, NOT in place. v1 fixtures stay frozen until v1 is sunset; both stacks keep their v1 contract tests as long as the wallet still ingests v1 envelopes during the migration window.

## 8. What's deliberately not fixtured (v1)

- **Network-level concerns** (TLS handshake, mTLS, HTTP framing). These belong in integration tests against a real server.
- **Persistence layer** (Postgres rows, Flyway migrations). Server tests cover these against Testcontainers; fixtures stay above DB.
- **Argon2id timing budget** on web. Tracked separately as a perf budget in CI (web Argon2id at the web floor must complete within 4s wall-clock on a defined runner profile), not as a byte-level fixture.
- **Random session tokens / challenge nonces in flight**. The fixture covers signing them deterministically; production paths use the live CSPRNG.

## 9. Working agreement

- A stack disagreeing with the fixture is a **bug in the stack** unless `tools/gen.py` is also wrong, in which case the fix is: (1) fix `gen.py`, (2) regenerate, (3) update committed fixtures, (4) re-run both stack tests, (5) one PR with all of the above.
- Never "fix" a stack by editing committed fixture bytes without regenerating from `gen.py` — that decouples the fixture from its inputs and the next regeneration silently flips it back.
- Fixture changes are reviewed with the same scrutiny as crypto code. The CODEOWNERS file lists at least two reviewers for `spec/fixtures/**` and `spec/tools/**`.
